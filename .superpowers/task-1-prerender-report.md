# Task 1 report: static pre-rendering for the four public pages

## Summary

The build now pre-renders the four public routes (`/`, `/pricing`, `/terms`, `/privacy`) to real
HTML files. The build produces no Node server. Every other route stays client-rendered. All seven
verification checks pass, with real output recorded below.

## Files changed

### `frontend/package.json`
Added `@angular/platform-server` and `@angular/ssr` as dependencies, and `@types/node` as a dev
dependency. These packages run the pre-render step at build time. No script for a Node server
runtime was added; an earlier draft of `serve:ssr:frontend` was removed (see "The server.ts
decision" below).

### `frontend/package-lock.json`
Updated to match `package.json`. No existing package changed version. The `@angular/ssr` schematic
also bumped `@types/node` and its transitive `undici-types` dependency, because the schematic adds
an explicit `@types/node` range where none existed before.

### `frontend/angular.json`
Added three keys to the `build` target: `"server": "src/main.server.ts"`, `"outputMode": "static"`,
and `"security": { "allowedHosts": [] }` (the schematic default). `outputMode: "static"` is the key
setting: it makes the build emit only `dist/frontend/browser` (the plain static site), with no
server bundle. Confirmed by inspecting the output folder after two full builds: no
`dist/frontend/server` directory exists in either build.

### `frontend/tsconfig.app.json`
Added `"node"` to the `types` array. The server bootstrap file needs Node type definitions to
compile.

### `frontend/src/app/app.routes.server.ts` (new)
Lists the four public paths with `RenderMode.Prerender`, and a catch-all `**` with
`RenderMode.Client`. This is an explicit list, not a catch-all default, so a future route added to
`app.routes.ts` stays client-rendered unless a developer deliberately adds it here.

### `frontend/src/main.server.ts` and `frontend/src/app/app.config.server.ts` (new)
Generated by the `@angular/ssr` schematic, unedited. They wire the server-side bootstrap and merge
`provideServerRendering(withRoutes(serverRoutes))` into the app config used only during the
pre-render build step.

### `frontend/src/app/app.config.ts`
Added `provideClientHydration(withEventReplay())` to the providers list. The schematic added this
automatically. `withEventReplay()` queues a click on the pre-rendered page (for example, a nav
link) and replays it once Angular finishes hydrating, so an early click still works.

### `frontend/src/app/app.ts`
Guarded the fire-and-forget `void this.userStore.refresh()` call with
`isPlatformBrowser(inject(PLATFORM_ID))`. This was the critical hazard named in the task: this
call performs an HTTP GET to `/v1/me` on the live API. Without the guard, every pre-rendered page
would call the production API at build time. The guard keeps the call exactly as it was in the
browser, and skips it entirely during the server-side pre-render pass.

### `frontend/public/_redirects`
Removed six rows: `/pricing`, `/pricing/`, `/terms`, `/terms/`, `/privacy`, `/privacy/`. Added one
comment line stating that a pre-rendered route must not have a row. Every other row is untouched.
The comment block at the top of the file is untouched. There was no row for `/`, so none was
removed for the landing page.

## The server.ts decision

The task names three files to accept from the schematic: `main.server.ts`, `app.config.server.ts`,
`app.routes.server.ts`. It does not name the fourth file the schematic generated,
`src/server.ts` — an Express server wrapper meant to run `dist/frontend/server/server.mjs` as a
live Node process. This directly conflicts with the constraint "do not introduce a server
runtime," so I removed it. I also removed the `ssr.entry` key from `angular.json` that pointed to
it, the `express` and `@types/express` packages, and the `serve:ssr:frontend` npm script. I
rebuilt after each removal: the build still pre-renders all four routes and still produces no
`dist/frontend/server` directory, so the file was not needed for the static build.

## The @angular/ssr peer-dependency conflict (worth knowing about)

`npx ng add @angular/ssr --skip-confirmation` failed on the first attempt with an `ERESOLVE` error.
The registry's newest `@angular/ssr` (20.3.34) triggered npm to try to raise `@angular/router` to
20.3.29, and Angular's own framework packages pin exact peer versions against each other
(`@angular/router@20.3.29` requires `@angular/core` at exactly `20.3.29`). The project's other
Angular packages are pinned at `20.3.27`. Raising router alone, without also raising core, common,
forms, and platform-browser, produces an unsatisfiable peer graph. This is a real Angular version
change, which the task told me to stop and report rather than improvise around.

I did not take that path. Instead I pre-installed `@angular/ssr@20.3.27` and
`@angular/platform-server@20.3.27` — the exact version already used by the rest of the framework —
with `npm install --legacy-peer-deps` for just that one step, before running `ng add` again. With
the packages already present, `ng add` skipped its own install step, ran only the file-generation
schematic, and its own later "Installing packages" step (with the schematic's looser
`^20.3.33`/`^20.3.0` ranges written into `package.json`) resolved cleanly on its own, landing on
`@angular/ssr@20.3.34` without moving `@angular/core`, `@angular/router`, `@angular/common`,
`@angular/forms`, or `@angular/platform-browser` off `20.3.27`. I verified this by checking every
framework package's resolved version in `node_modules` after each install step. No Angular
framework version changed at any point. `@angular/ssr` itself is a brand-new addition, so its own
version is not "an existing dependency being upgraded."

## SSR hazards checked

I read every component reachable from the four public routes, the root `App` shell, and everything
it imports, and searched the whole `src/app` tree for `window.`, `document.`, `localStorage`,
`sessionStorage`, and `navigator.` outside spec files.

- **`app.ts`** — HAZARD, fixed. Constructor called `userStore.refresh()` unconditionally (an HTTP
  GET to the live API). Now guarded with `isPlatformBrowser`.
- **`app.html`** — reads two signals (`userStore.user()`, `siteContext.domain()`). Both default to
  a safe value with no side effect. Safe.
- **`landing.ts`** — `sessionStorage.setItem` only inside the `submit()` click handler. Confirmed
  as already-safe per the task brief. Safe.
- **`pricing.ts`** — `ngOnInit` calls `init()`, which reads `store.user()` and returns early when
  there is no signed-in user. Confirmed as already-safe per the task brief. Since `app.ts` no
  longer populates the store during pre-rendering, `store.user()` stays `null` at render time, so
  this early return always fires during the build. Safe.
- **`terms.ts`, `privacy.ts`** — pure static templates, no injected services, no lifecycle hooks.
  Safe.
- **`shared/site-footer.ts`, `shared/score-bar.ts`, `shared/impact-badge.ts`,
  `features/pricing/plan-cards.ts`** — pure presentational components with `input()`/`output()`
  only. No injected `HttpClient`, no browser globals. Safe.
- **`features/pricing/upgrade-flow.ts`** — `document.createElement` and `window` access live
  inside `loadFreemiusScript()` and `openCheckout()`, both called only from a user click
  (`Pricing.unlock()`), never from a constructor or `ngOnInit`. The class has no explicit
  constructor; its only field initializers are `inject(ApiClient)` and `inject(UserStore)`, which
  touch no browser globals. Safe.
- **`core/auth/user-store.ts`, `core/api/api-client.ts`, `core/api/credentials.interceptor.ts`,
  `core/site-context.ts`, `core/config.ts`, `shared/copy.ts`** — every HTTP call is defined inside
  a method, never fired from a field initializer or constructor. `core/site-context.ts` is a plain
  signal store. `core/config.ts` and `shared/copy.ts` export pure constants and functions. Safe.
- **`core/auth/guards.ts`** (`authGuard`, `guestGuard`) — imported eagerly by `app.routes.ts`, but
  the guard bodies (which call `store.refresh()`) run only when a *guarded* route activates. None
  of the four pre-rendered paths carry a guard, so these bodies never execute during pre-rendering.
  Safe.
- Two hazards found outside the four-route tree, confirmed out of scope: `dashboard.ts` and
  `features/site-home/skips.ts` both use `sessionStorage`, but `dashboard` and `sites/:siteId` are
  both behind `authGuard` and rendered with `RenderMode.Client`. Not touched.

## Concerns

- The Playwright run logs one warning from the Angular dev server used by its own local test
  harness: `NG02801: HttpClient is not configured to use fetch APIs... recommended... for
  Server-Side Rendering`. This is Angular recommending `withFetch()` on `provideHttpClient()` for
  best hydration performance. It is a recommendation, not an error, and every test still passes.
  I left `provideHttpClient` unchanged because the task asks for no behaviour change beyond what
  is required, and adding `withFetch()` was not requested. A follow-up task could add it.
- The `npm audit` output shows one pre-existing high-severity advisory (`nanoid` `<3.3.18`,
  transitive, from `karma`/testing tooling). I confirmed this package and version
  (`nanoid@3.3.17`) were already present in `package-lock.json` before this task started, and
  the `express` removal in this task actually reduced dependency count. Not introduced by this
  work, and out of scope to fix here.
- `frontend/dist` is git-ignored, so the pre-rendered output itself is not part of this commit.
  Cloudflare Pages regenerates it from `npm run build` on deploy.
